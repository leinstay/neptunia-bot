Neptunia запускается локально и играет в Discord одного настраиваемого персонажа через LLM, ведя себя как обычный участник чата. Работает на Node.js 20+ с единственной зависимостью (discord.js) и с любым OpenRouter-совместимым эндпоинтом. Карточка персонажа подключается без правки кода, промпты и конфигурация перезагружаются на лету, есть память по каждому участнику с отношением и эпизодами, серверный лорбук, зрение для прикреплённых картинок, однострочные описания медиа от вспомогательной модели, слэш-команды владельца для настройки на лету и режим сухого прогона. В комплекте рабочий пример персонажа; для другого персонажа напишите свою карточку.

Персонаж отвечает на упоминания, ответы и триггеры по имени, иногда игнорируя их. Он вклинивается в разговоры через случайные интервалы и заводит темы в мёртвых каналах. Он запоминает людей, отслеживает отношение от -100 до 100 и учитывает его в ответах. Сам балл в чате не показывается. Вся конфигурация и промпты перезагружаются на лету; команды владельца настраивают бота прямо из Discord.

Каждый экземпляр обслуживает один сервер, один аккаунт бота, одну личность. Для второго сервера или персонажа запустите вторую копию со своими `.env`, `config.local.json`, `prompts.local/` и `data/`. Discord помечает бот-аккаунты значком APP; движок этого не скрывает.

## Быстрый старт

Создайте приложение Discord на [discord.com/developers](https://discord.com/developers/applications). Включите привилегированный интент **Message Content** на странице Bot. В ссылке приглашения нужны оба scope (`scope=bot%20applications.commands`) и `permissions=68672` (просмотр каналов, отправка сообщений, чтение истории, добавление реакций). Если слэш-команды не появились после добавления бота, причина будет в логе; достаточно снова открыть ссылку приглашения и пройти её заново, удалять бота не нужно.

Получите API-ключ на [OpenRouter](https://openrouter.ai/keys) (или на любом совместимом эндпоинте).

```bash
git clone https://github.com/leinstay/neptunia-bot.git
cd neptunia-bot && npm install
cp .env.example .env
```

Отредактируйте `.env`, указав токен Discord и API-ключ. Создайте `config.local.json` со своим Discord user ID:

```json
{
  "bot": {
    "owners": ["YOUR_DISCORD_USER_ID"]
  }
}
```

```bash
npm start
```

Когда `bot.guildId` пуст и бот находится ровно на одном сервере, он привязывается к нему автоматически. Если бот на нескольких серверах, он откажется запускаться. Укажите `bot.guildId` в `config.local.json`.

## Слои промптов

Промпты загружаются из двух директорий:

- `prompts/`: дефолты движка из репозитория. Содержат рабочий пример персонажа.
- `prompts.local/`: ваш персонаж (в gitignore). Файл здесь заменяет одноимённый файл в `prompts/`. `labels.json` объединяется глубоким слиянием, так что вы переопределяете только нужные ключи.

Оба каталога перезагружаются на лету.

### Файлы промптов

| Файл | Обязателен | Назначение |
|---|---|---|
| `system-prompt.md` | да | Как вести себя обычным участником чата, без привязки к персонажу |
| `character-card.md` | да | Личность: кто это, как говорит, что для него важно |
| `rules.md` | нет | Правки владельца на лету, добавляются через `/nep rule add` |
| `format.md` | да | Протокол вывода: теги, через которые модель действует |
| `reply.md` | да | Задача: кто-то обратился к персонажу |
| `interject.md` | да | Задача: вклиниться в живой разговор |
| `initiate.md` | да | Задача: нарушить тишину, начать тему |
| `memory.md` | да | Технический промпт для анализатора памяти и отношений |
| `describe.md` | да | Однострочные описания медиа для вспомогательной модели |
| `address.md` | да | Классификатор: адресовано ли сообщение без обращения персонажу |
| `profile.md` | да | Прогрев: профиль одного участника из выборки сообщений |
| `channel.md` | да | Прогрев: заметки о канале из выборки сообщений |
| `server.md` | да | Прогрев: серверные заметки из заметок каналов и сводок участников |
| `labels.json` | да | Все строки, которые код вставляет в промпты (глубокое слияние между слоями) |

**Единственный файл, который нужно переписать: `character-card.md`.** Скопируйте его в `prompts.local/` и опишите своего персонажа. Всё остальное работает из коробки; при необходимости переопределяйте отдельные файлы.

Анализатор памяти оценивает, как персонаж относится к людям. И анализатор, и прогрев получают вашу карточку персонажа и `rules.md`, поэтому укажите, что ваш персонаж любит и не любит.

Плейсхолдеры, ключи `labels.json`, контекстные блоки и теги вывода, которые может использовать каждый файл промпта, описаны в [`docs/prompt-contract.md`](../prompt-contract.md); изменение одной стороны требует изменения другой.

## Конфигурация

`config.json` содержит все настройки с дефолтами. `config.local.json` (в gitignore) объединяется глубоким слиянием поверх него. Оба перезагружаются на лету. Полный справочник по всем ключам: [`configuration.md`](configuration.md).

## Прогрев

При первом запуске, если `warmup.enabled` включён и ни одного профиля ещё нет, движок запускает прогрев, который строит память о людях, каналах и сервере из выборки недавних сообщений. Общий расход токенов ограничен `warmup.maxTokens`. Персонаж молчит, пока идёт прогрев. Этапы, прогресс, ограничения и команды владельца описаны в [`warmup.md`](warmup.md).

## Сухой прогон

При `features.dryRun: true` бот выполняет весь пайплайн (память, триггеры, вызовы LLM), но не отправляет ни сообщений, ни реакций. Вывод попадает в лог (`dry-run: would send` / `dry-run: would react`). Укажите в `bot.dryRunChannelId` приватный канал, чтобы получить читаемое зеркало; всё, что публикуется в этом канале, бот игнорирует. Слэш-команды работают в любом канале, включая зеркало, потому что это не сообщения.

Первый запуск на новом сервере: включите `features.dryRun`, следите за зеркалом или `journalctl -u neptunia-bot -f`, настраивайте на лету, затем `/nep set features.dryRun false`.

## Команды

Одна слэш-команда Discord: `/nep` (имя задаётся в `bot.commandName`). Команда регистрируется при запуске как гильдийная, только для обслуживаемого сервера. Все ответы эфемерные; их видит только тот, кто вызвал команду, в каком бы канале она ни была введена. Полный список подкоманд и разрешения доступа: [`owner-commands.md`](owner-commands.md).

## Обработка сообщений

Сообщение проходит фильтры гильдии, канала и собственных сообщений. Если персонажа вызвали (@упоминание, ответ или триггер по имени), срабатывает бросок на игнорирование против базовой вероятности с поправками на пустые пинги, повторные теги, спам и балл отношения к вызвавшему. После того как персонаж ответил кому-то, сообщения без обращения в этом канале в течение следующих `mention.followUpMinutes` минут отправляются классификатору на роли модели `followUp` (по умолчанию медиа-модель), который определяет, продолжается ли разговор; три `no` подряд закрывают окно. Отключается через `features.followUp`. Спонтанные ходы срабатывают от хаотичного таймера или от шанса подслушивания на каждое сообщение. Персонаж не заговорит без повода в канале, молчащем более `spontaneous.maxChannelSilenceHours` часов; прямой пинг при этом по-прежнему получит ответ.

Персонаж пишет один ответ за раз на весь сервер. Пинг в том же канале, пока он уже отвечает, пропускается; пропущенные сообщения попадут в транскрипт при сборке следующего ответа. Прямой пинг в другом канале (@упоминание или ответ на его сообщение, не триггер по имени) откладывается: по одному на канал, не больше чем в `mention.maxPending` каналах, на `mention.pendingMinutes` минут; новый пинг в том же ожидающем канале заменяет предыдущий. Когда текущий ответ завершается, персонаж переключается на канал после короткой паузы (`mention.switchDelayMs`) и отвечает исходя из разговора в его текущем виде; обычный шанс игнорирования действует и здесь. Триггеры по имени и срабатывания подслушивания, пришедшие во время занятости, пропускаются. При `mention.oneAtATime: false` каждый канал обрабатывается независимо. Персонаж никогда не пишет и не реагирует там, где у него нет права Send Messages; проверка идёт до того, как потрачен запрос к LLM; такие каналы по-прежнему читаются и запоминаются.

Ход собирает транскрипт канала и соседние каналы, затем строит один запрос к LLM в рамках бюджета токенов. Секции заполняются в порядке приоритета: системный промпт и задача никогда не обрезаются; далее профиль вызвавшего, серверные привычки и факты о себе, карта каналов, транскрипт (новейшие сначала), другие профили и соседние каналы. Модель видит карту каналов сервера (назначение, темы, тон, уровень активности), текущий канал отмечен. Каждая запись канала также содержит факты, которые ведёт код: количество сообщений, первое и последнее сообщение, активность за последние 30 дней и самых активных авторов; прогрев заполняет их из истории канала, а живой трафик поддерживает актуальность.

Модель отвечает тегами `<think>` (скрытое планирование), `<msg>` (1–3 сообщения; `reply="#87"` отвечает на строку транскрипта), `<react>` (одна эмодзи-реакция) или `<skip/>` (молчание). После разбора ответа имитируется набор текста с человеческой скоростью, а `@nick` в выводе становится реальным упоминанием.

Анализатор памяти запускается как отдельный вызов LLM, когда накопится достаточно сообщений. Он получает карточку персонажа и оценивает каждого человека глазами персонажа, возвращая сдвиги отношения, правки профилей, наблюдения по каналам и серверные заметки. Портрет характера и манеры речи участника строится из каналов в `memory.mainChannelIds`; если список пуст, учитываются все каналы. Профили обновляются инкрементально: анализатор возвращает только изменившееся, а сохранённые факты не пересказываются. Характер и стиль хранятся как прозаические абзацы: их целиком пишет промпт профиля во время прогрева и обновляет по недавним сообщениям, когда анализатор отмечает пробел или противоречие. Интересы и детали хранятся отдельными элементами; элемент считается подтверждённым, когда всплывает снова в другой раз; на каждого человека хранится больше элементов, чем показывается, ранжированных по частоте и новизне с весом, который убывает со временем. Интересы, которые давно не встречались, показываются персонажу как устаревшие. Сохранённая память ссылается на участников по id, а текущее имя подставляется в момент использования, поэтому переименования не ломают сохранённые заметки. Персонаж также запоминает, как люди в чате называют друг друга, и узнаёт участника, упомянутого по имени или псевдониму, даже если тот не участвует в разговоре.

## Эпизоды и лорбук

Анализатор памяти ведёт два типа долгосрочных заметок помимо профилей.

Эпизоды хранят моменты, которые персонаж запомнил о конкретных людях: оскорбление, доброту, обещание, пари, общую шутку, просьбу что-то сделать или никогда не делать. Анализатор добавляет их в профиль человека с датой, кратким описанием, иногда словами самого человека и весом от 1 до 5. Самые весомые живут дольше всех; когда профиль достигает `memory.maxEpisodes`, сначала вытесняются самые лёгкие, затем самые старые. Показываются только эпизоды вызвавшего, внутри блока `<people>`.

Лорбук хранит серверные знания, которые переживают любой разговор: события, повторяющиеся персонажи, длительные истории, конфликты, традиции. Каждая запись имеет заголовок, набор ключевых слов и короткий текст. Код сканирует последние `lore.scanMessages` сообщений на совпадения ключевых слов и включает до `lore.maxMatches` записей в блок `<lore>`; записи с пометкой `always` появляются каждый раз. Записей могут быть сотни, и это почти ничего не стоит: показываются только те немногие, что совпали.

Анализатор добавляет и обновляет записи лорбука самостоятельно, но никогда не трогает записи, добавленные владельцем через команды `/nep lore`. Данные лорбука хранятся в `data/guilds/<id>/lore.json`.

## Зрение и медиа

Строки транскрипта содержат маркеры медиа в скобках: картинки, GIF, видео, стикеры, кастомные эмодзи, голосовые сообщения, аудиофайлы, ссылки, превью текстовых файлов и пересланные сообщения. Пересланные сообщения из другого канала того же сервера указывают канал-источник. Что воспринимает персонаж, зависит от двух настроек.

`features.vision` прикрепляет картинки из вызвавшего сообщения, из сообщения, на которое оно отвечает, и несколько последних в канале к запросу LLM как изображения, уменьшенные через медиа-прокси Discord. Бот скачивает каждую картинку сам и отправляет её инлайн как данные, потому что Discord не отдаёт файлы по запросам от провайдера модели; картинки больше `context.vision.maxBytes` или не скачавшиеся за `context.vision.fetchTimeoutMs` пропускаются. Персонаж видит их напрямую. Настройки находятся в `context.vision`.

`features.mediaDescriptions` (включён по умолчанию) запускает вспомогательную модель (`media.model`), которая пишет однострочное описание для картинок, кадров GIF, постеров видео, стикеров, кастомных эмодзи и превью ссылок. Каждое вложение описывается один раз и кэшируется. Описания поступают в транскрипт чата, анализатор памяти и прогрев; описания во время прогрева оплачиваются из его бюджета токенов. Промпт модели описаний: `prompts/describe.md`. Настройки находятся в `media`.

Стикеры и кастомные эмодзи постоянно повторяются, поэтому кэшируются по id и почти ничего не стоят после первого описания. При `features.vision` стикер вызвавшего сообщения прикрепляется как картинка. Встроенные анимированные стикеры Discord хранятся как Lottie-анимации, а не как картинки, поэтому от них остаётся только название.

Блок `<senses>` в пользовательском сообщении говорит персонажу, что он может и чего не может воспринимать при текущей конфигурации. Персонаж доверяет этому блоку и никогда не утверждает, что видел, слышал или открывал что-то сверх указанного.

Персонаж не может смотреть видео или слушать аудио; ему доступны имя, длительность и в лучшем случае описание одного кадра. Голосовые сообщения показывают только длительность. Ссылки показывают сайт, заголовок и фрагмент из эмбеда Discord, но не саму страницу.

## Стоимость и конфиденциальность

Каждый ход стоит один запрос к LLM; обновление памяти добавляет второй. Стоимость зависит от модели и эндпоинта; `llm.model` и `llm.baseUrl` принимают любые совместимые значения. Дневной лимит (`llm.maxRequestsPerDay`) предотвращает неконтролируемые расходы.

`data/` содержит профили участников, баллы отношений, наблюдения по каналам и серверные паттерны. Всё остаётся на вашей машине, включено в gitignore и отправляется в LLM только как контекст. Анализатору дана инструкция не хранить конфиденциальные данные. `/nep memory forget` полностью удаляет профиль.

Предупредите участников сервера. Они должны знать, что их сообщения обрабатываются LLM и что бот ведёт заметки.

## Запуск как сервис

Пример юнита systemd: `deploy/neptunia-bot.service`. Настройте `WorkingDirectory` и `User`, затем установите:

```bash
sudo cp deploy/neptunia-bot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now neptunia-bot
```

Приватный слой живёт рядом с кодом: `.env`, `config.local.json`, `prompts.local/`, `data/`. Обновление:

```bash
git pull && sudo systemctl restart neptunia-bot
```

При перезапуске ничего не теряется; всё состояние на диске. Перезапуск нужен только после изменений кода в `src/`. Правки промптов и конфигурации применяются на лету.

Память живёт в процессе и записывается в `data/`; редактирование этих файлов при работающем боте небезопасно, так как следующая запись затрёт правку. Чтобы править память вручную: `/nep pause`, правка файлов, `/nep resume`. Пауза останавливает всю активность, сбрасывает память на диск и выгружает её; запущенный прогрев приостанавливается после текущего запроса. Состояние сохраняется: после перезапуска бот остаётся на паузе, и прогрев не стартует автоматически до возобновления. `/nep resume` проверяет каждый JSON-файл в `data/` и отказывает, если хоть один не разбирается, перечисляя сломанные; иначе перезагружает память и продолжает, включая прогрев с места остановки. Команды чтения и конфигурации работают на паузе; команды записи памяти отклоняются. `/nep status` показывает состояние паузы.

## Участие в разработке

Приветствуются issues и pull requests; сначала прочитайте `CONTRIBUTING.md`. Целевая ветка `main`, одно изменение на pull request, тесты проходят (`npm test`), всё на английском. Контракт между файлами промптов и кодом описан в `docs/prompt-contract.md`. Изменение одной стороны требует изменения другой в том же pull request. Движок остаётся нейтральным к персонажу; поведение конкретного персонажа живёт в `prompts.local/` конкретного развёртывания. Об уязвимостях сообщайте по `SECURITY.md`, а не в публичных issues.

## Тесты

```bash
npm test
```

Запускается через `node --test`. Ни сеть, ни подключение к Discord не нужны. Та же команда выполняется в CI при каждом pull request.
